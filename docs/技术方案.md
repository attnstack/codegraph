# codegraph 技术方案

> **定位**：用 AST 把代码库解析成可查询的知识图谱——无需向量库，所有检索结果确定、可解释、能给出证据调用链；支持增量更新；MCP + CLI 双出口
> **角色**：面试主项目 C（深度担当）——覆盖维度：②算法 + ①系统设计；天然命中编译原理 / 图算法 / 系统设计 / 数据结构四类面试高频硬考点，且不易被怀疑"调 API"
> **版本**：v1.0 · 2026-10-29
> **工期**：Week 4–6（三周，慢慢磨）
> **依据**：《面试导向项目包装方案》项目 C + 《GitHub 高星项目技术方案集》项目⑥

---

## 1. 项目概述

### 1.1 一句话 Pitch

> 「用 AST 把代码库解析成可查询的知识图谱，不需要向量库，所有检索结果都是确定的、可解释的、能给出证据路径。支持增量更新，接入 MCP。」

### 1.2 为什么选它做深度担当

| 面试考点 | 对应模块 |
|---|---|
| 编译原理（AST、tree-sitter） | 解析与符号解析 |
| 图算法（BFS 闭包、PageRank） | 影响面分析 / hotspots |
| 系统设计（增量更新、存储选型） | 增量引擎 / SQLite 图存储 |
| 数据结构（索引、剪枝） | 引用索引 / 剪枝策略 |

### 1.3 目标与非目标

| 目标 | 非目标 |
|---|---|
| MVP 支持 TypeScript/JavaScript（tree-sitter 生态最成熟） | 不追求全语言覆盖（架构插件化，覆盖面是工程量问题，查询质量是设计问题——这个优先级判断本身是面试加分点） |
| 每条查询结果附完整证据链 | 不做语义相似度搜索（不用向量库，这是差异化不是缺陷） |
| 万行级仓库增量更新毫秒级 | 不做实时 IDE 级诊断（LSP 是另一个赛道） |
| MCP Server + CLI 双接口 | 不做代码生成/改写 |

### 1.4 竞品与差异化

- Graphify（AST→知识图谱，131K 星）、codebase-memory-mcp（tree-sitter 158 语言，省 99% token）验证了赛道。
- **差异化主论点（面试主动抛出）**：向量检索在代码场景有两个硬伤——①返回"语义相近"而非"真有调用关系"，会给错误答案；②不可解释，不知道为什么返回它。AST 图谱的关系是确定的，结果可解释、可验证。**代价**是解析成本与语言覆盖，用增量更新摊薄。主动承认局限比被追问出来强一百倍。

## 2. 总体架构

```
文件发现(gitignore感知+排除规则) ──► tree-sitter 解析 ──► 符号解析/建边 ──► SQLite 图存储
                                                              │
              git 历史(blame + log) ──────────────────────────┤
                                                              ▼
                                   查询层(who-calls/impact/trace/hotspots/archaeology)
                                                        ┌─────┴─────┐
                                                        ▼           ▼
                                                   MCP Server     CLI
                                                    (stdio)
```

**技术栈**：Rust（核心：解析、图构建、查询、MCP stdio——单二进制零依赖，对标 codebase-memory-mcp 的分发卖点）+ TypeScript（MCP 客户端契约测试与集成 harness；可选 napi-rs 绑定发 npm 包方便 Node 生态分发）。存储 SQLite（rusqlite）。

## 3. 图模型设计

### 3.1 节点与边

| 节点类型 | 属性 | 边类型 |
|---|---|---|
| File / Module | path, hash, loc, mtime | contains, imports |
| Class / Interface | name, visibility, span, doc_anchor | extends, implements |
| Function / Method | name, signature, span, is_exported, cyclomatic | calls, called_by, overrides |
| API Route | method, path | handled_by, returns |
| DB Table / Model | name | reads, writes |

节点唯一键：`(repo, path, kind, name, span)`。所有节点记录定义处 `file_id + byte_span`，保证结果可跳转源码（可解释性的物理基础）。

### 3.2 语言扩展机制（插件化）

```rust
trait LanguageAdapter {
    fn id(&self) -> &'static str;                  // "typescript"
    fn grammar(&self) -> tree_sitter::Language;
    fn queries(&self) -> &'static str;             // .scm 抽取规则
    fn map_node(&self, kind: &str) -> Option<NodeKind>;  // AST 节点 → 图节点映射
    fn resolve_import(&self, spec: &str, from: &Path) -> Option<PathBuf>;
}
```

加一门语言 = 补 grammar 依赖 + queries 文件 + 节点映射表。MVP 实现 `typescript`（含 TSX/JS）。

## 4. 解析与符号解析

### 4.1 tree-sitter queries 示例（TypeScript 抽取）

```scheme
; 函数定义
(function_declaration name: (identifier) @def.name) @def.func
; 方法定义
(method_definition name: (property_identifier) @def.name) @def.method
; 类定义
(class_declaration name: (identifier) @def.name) @def.class
; 调用点
(call_expression function: (identifier) @call.name) @call.expr
(call_expression function: (member_expression
    property: (property_identifier) @call.prop)) @call.method-expr
; import
(import_statement source: (string) @import.spec) @import.stmt
```

### 4.2 引用解析三级策略

1. **同文件**：文件内符号表直接命中；
2. **import 图**：沿该文件的 import 解析到目标模块导出符号；
3. **全局**：跨文件索引兜底。
无法消歧（同名重载 / 动态调用 / `any` 类型）→ **不猜**，调用点标记为 `dynamic`，影响面分析中作为"间接影响"单独列出。宁缺毋滥是确定性承诺的一部分。

## 5. 存储设计（SQLite）

```sql
CREATE TABLE files(id INTEGER PRIMARY KEY, path TEXT UNIQUE, hash TEXT,
                   mtime INTEGER, loc INTEGER);
CREATE TABLE nodes(id INTEGER PRIMARY KEY, kind TEXT, name TEXT, file_id INTEGER,
                   span_start INTEGER, span_end INTEGER, is_exported INTEGER,
                   extra JSON);
CREATE TABLE edges(src INTEGER, dst INTEGER, kind TEXT, weight INTEGER DEFAULT 1,
                   evidence TEXT,          -- 调用点 span，构成证据链
   PRIMARY KEY(src, dst, kind));
CREATE INDEX idx_nodes_name ON nodes(kind, name);
CREATE INDEX idx_edges_dst ON edges(kind, dst);   -- 反向查询(called_by)走这个
CREATE INDEX idx_edges_src ON edges(kind, src);
```

导出：DOT / GraphML / 只读 Cypher 片段（便于用户导入 Neo4j 可视化）。

## 6. 查询与核心算法

### 6.1 影响面分析（必讲亮点 1）

「改这个函数会影响哪些地方？」

```
1. 起点 = 目标符号节点
2. 反向闭包 BFS，边集 = {called_by, overridden_by, extends, implements, imported_by}
3. 剪枝（直接 BFS 会爆炸）：
   a. 路径规则排除 test|spec|__tests__|generated|vendor|node_modules|dist（可配）
   b. dynamic 调用点不展开，标记"间接影响"
   c. 深度上限（默认 8）+ 节点数上限（默认 500），超限输出截断统计
4. 风险评分：risk(n) = Σ_paths w^dist × type_w
     type_w: 直接调用 1.0 / 继承重写 0.7 / 动态调用 0.5；w = 0.8（每跳衰减）
5. 输出：按 risk 排序的影响清单；每项附完整证据调用链 A → B → C
   （链上每个环节都有 edge.evidence = 源码位置）
```

**关键点**：返回证据链而不是"模型觉得有关"——这是"可解释"的落地，也是 README 标题句。

### 6.2 核心路径打分（hotspots）

- 在调用图子图上跑加权 PageRank：边权 = 调用次数；跨文件调用额外 ×1.5（跨模块耦合比文件内更值得警惕）；阻尼 0.85，迭代至 L1 差 < 1e-6。
- 用途：新人上手"先读这 5 个文件"；重构高风险区提示。

### 6.3 trace（链路追踪）

`trace <entry> <sink>`：双向 BFS（从入口正向、从目标反向，各限深 5，相遇即得路径），返回入口到 DB/外部调用的完整链路。

### 6.4 时间维度考古（archaeology，传播性最强的功能）

```
输入: 符号或行范围
1. git blame -C 定位引入行 → commit
2. git log 还原该 commit 的 message / 关联 PR / 当时的上下文
3. 聚合 blame 贡献度 → "谁最懂这块代码"
回答："这段逻辑为什么这样写"（定位引入 commit 与动机）
```

### 6.5 增量更新（必讲亮点 3）

- **双驱动**：`notify` crate 文件 watcher（开发态）+ `git diff`（提交态 / CI）。
- **失效范围**：重解析变更文件 + 沿 `called_by / imported_by` 反向依赖一层（它们的出边可能失效）。
- **一致性保证**：查询前校验文件 hash，脏则即时重解析该文件（毫秒级）或结果标注「基于 commit X」的 stale 标记。
- **性能口径**：冷启动全量解析 10 万行 TS 仓库目标 < 30s（实测填入）；增量单文件变更 < 200ms。

## 7. MCP 工具与 CLI

### 7.1 MCP tools（对接 Claude Code / Cursor 等 Agent）

| tool | 输入 | 输出 |
|---|---|---|
| `who_calls` | symbol | 调用方列表 + 位置 + 证据链 |
| `impact` | symbol, depth? | 风险排序影响清单 + 证据链 |
| `trace` | entry, sink | 完整调用链 |
| `hotspots` | top_k? | PageRank 核心函数 |
| `archaeology` | symbol 或 file:line | 引入 commit / PR / 贡献者 |
| `search` | query | 符号搜索（精确/前缀） |

### 7.2 CLI 输出示例

```
$ codegraph impact src/services/payment.ts::charge
影响面分析（8 个直接受影响节点，3 个动态间接影响已折叠）:
 1. ▲ risk 0.84  checkout.ts::createOrder        ← charge ← createOrder (src/checkout.ts:88)
 2. ▲ risk 0.55  refund.ts::processRefund        ← charge ← processRefund (src/refund.ts:41)
 ...
 证据链均可跳转源码；动态调用点 3 处（见 --show-dynamic）
```

## 8. 测试与质量

| 层 | 方式 |
|---|---|
| 单元 | 符号解析 / 建边 / 剪枝规则逐条测 |
| Golden snapshot | 每个夹具仓库（手工构造的小 TS 仓库）的图输出快照 |
| **增量一致性 fuzz** | 随机变异文件序列，断言"增量结果 == 全量重建结果"（核心正确性测试） |
| 真实仓库回归 | 固定 3 个开源 TS 仓库的固定 commit，跑全套查询做性能与结果回归 |
| 性能回归 | 解析耗时 / 增量耗时进 CI，超阈值报警 |

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| 动态调用 / any 类型无法静态解析 | 不猜：标 `dynamic` 为"间接影响"，诚实呈现不确定性 |
| tree-sitter grammar 版本升级 breaking | grammar 版本锁定在 Cargo.lock；queries 有 CI 回归 |
| 超大 monorepo 内存峰值 | 按文件流式构建 + 节点批量写库 + 上限熔断 |
| 图谱随代码演进失效 | hash 校验 + 即时重解析 + stale 标注双保险 |

## 12. 面试作战手册

### 12.1 三个技术亮点

1. **影响面分析 + 证据链**：反向闭包 BFS 为什么要剪枝（测试/generated/vendor 会爆炸）+ 距离权重风险排序 + 每条结果返回完整调用链。
2. **为什么不用向量检索（主动抛出）**：语义相近 ≠ 真有调用关系；不可解释。代价是解析成本与语言覆盖 → 增量更新摊薄。
3. **增量更新**：git diff 驱动，只重解析变更文件 + 反向依赖一层；fuzz 测试保证增量 == 全量。

### 12.2 高频追问

- **支持多少语言？为什么不全支持？** → MVP 只做 TS/JS（生态最成熟）；架构插件化，加语言 = grammar + queries + 映射；「覆盖面是工程量问题，查询质量是设计问题，我优先后者」——展现优先级判断力。
- **图谱会失效吧，怎么维护一致性？** → git hook 触发增量 + 查询前 hash 校验即时重解析 + stale 标注「结果基于 commit X」。
- **tree-sitter 抽取不到的信息怎么办（注解路由框架、DI 容器）？** → 承认静态分析边界；框架语义通过 adapter 的 map_node 扩展（如 Next.js 路由约定文件），不能覆盖的归入 dynamic。
- **如果重做会改什么？（必问）** → ① 引入 LSP 协议做前端交互而不仅 MCP/CLI；② 把符号解析从"三级策略"升级为类型推导（借 tsc API），消歧能力更强。

### 12.3 简历条目（数字实测后填）

```
codegraph-mcp · 代码库知识图谱引擎（Rust + TypeScript）
· 基于 tree-sitter 构建多语言代码图谱（文件/类/函数/路由/表 × 调用/继承/读写边），
  支持增量更新，十万行级仓库解析 <X 秒、增量 <X 毫秒
· 设计影响面分析算法：反向调用闭包 BFS + 剪枝策略（排除测试与生成代码），
  输出按风险排序的变更影响清单及完整证据调用链
· 引入加权 PageRank 定位核心函数，结合 git blame 实现代码考古（追溯引入 commit 与上下文）
· 提供 MCP Server 与 CLI 双接口，可对接主流 Agent
```
