## C1 追问链模拟（3 个核心技术点 × 5 层）

### 技术点 1：影响面分析（反向闭包 + 剪枝 + 风险排序 + 证据链）

- **L1 追问：影响面怎么算的？**
  答案要点：从目标符号出发，在调用图上做反向遍历（沿 called_by 方向），边集含
  调用、重写、继承、实现四类；每层按 `risk = parent_risk × 0.8 × type_w` 衰减打分，
  输出按风险排序；每个受影响节点附完整调用链，链上每跳都有源码位置。
- **L2 追问：为什么剪枝？不剪会怎样？**
  答案要点：不剪的话，改一个被测试大面积引用的工具函数，影响清单全是测试文件，
  真实业务影响被淹没；测试/生成代码/vendor 的传播不构成「改坏线上」的风险。
  剪枝规则用**路径分段精确匹配**（tests/__tests__/generated…）+ 文件名主干标记
  （.test/.spec），故意不用子串匹配——latest.ts 含 "test" 会被误杀。
- **L3 追问：闭包在有环图上会不会死循环？分数怎么收敛？**
  答案要点：visited 语义由 best-score 表承担——松弛只在分数**严格提高**时进入，
  环上每绕一圈分数乘 0.8 单调递减，分数下界使松弛有限次终止；另有深度上限 8、
  节点数上限 500 双熔断，超限输出 truncated 标记而不是悄悄截断。
- **L4 追问：risk 公式是 Σ 所有路径的权重和吗？**
  答案要点：不是，也**不能**是——Σ over simple paths 在有环图上是 #P-hard。
  我用单源最优路径近似：`risk(n) = max over in-edges (risk(p) × decay × type_w)`，
  Dijkstra 同型的最大堆松弛，O(E log V)。语义是「最坏传播强度」，
  对改代码决策恰好更有用；这是明知的有损近似，README 里写明了。
- **L5 追问：为什么用 max 而不是前 K 条路径求和，或者蒙特卡洛采样？**
  答案要点：K 短路径需要路径枚举（同样指数）或 Eppstein 算法（实现复杂度远超本项目
  全部算法之和）；蒙特卡洛在确定性工具里引入不确定性，与「结果可复现」冲突。
  max 语义下单调性成立（权重 < 1），Dijkstra 正确性有保证，且父指针顺手给出
  最坏路径作为证据链——工程与数学约束互相锁死时的最简正解。
  再追「多条路径影响叠加怎么办」：诚实回答——未建模，两条弱路径叠加可能被 max
  低估，这是记录在案的局限（README「不足」节）。
- **通常在第几层答不上**：L4 是分水岭（能否指出 Σ 的 #P 难并给出替代语义）；
  L5 考对替代方案的实现成本判断。要补的知识：Dijkstra 正确性证明要点（贪心选择性质
  在权重单调递减时成立）、#P vs NP 的区别（#P 数解个数，NP 判定解存在）。

### 技术点 2：增量更新为什么敢承诺「增量 ≡ 全量」

- **L1 追问：改一个文件后图谱怎么更新？**
  答案要点：mtime+size 预筛 → 内容 hash 确认 → 只重解析变更文件；
  符号解析对**全量视图**重跑（未变更文件的原材料在 DB 里，拉平即可）；
  refs/edges 全量重写，单事务提交。
- **L2 追问：为什么不只重算受影响的边（反向依赖一层）？那不是更快吗？**
  答案要点：正确性论证会爆炸——`export *` barrel 让依赖链传递、新增导出与删除导出
  的失效范围不同、重解析对方文件才能发现调用点失效。每个规则都是一个 stale-edge
  温床。我选「把贵的做增量（解析）、便宜的做全量（解析）」：符号解析是 O(refs)
  哈希查找，10 万行仓库毫秒级，换来的是正确性可以**被测试证明**而不只是被推理保证。
- **L3 追问：「增量 == 全量」怎么证明？**
  答案要点：fuzz 测试：固定 seed 随机变异（加函数/加文件/删文件/加注释移动 span/
  同名重载）10 轮，每轮之后（a）增量 update，（b）同一棵树全量重建到全新库，
  然后对两个库的**全部符号**跑 who_calls + impact 全查询电池，剥掉节点 id 后逐字段
  断言相等。等价性失效的任何回归都会被这个测试抓住。
- **L4 追问：跨进程的 hash 比较可靠吗？增量后节点 id 会乱吗？**
  答案要点：hash 用 DefaultHasher（SipHash-1-3 固定键），跨进程稳定——但我明确
  把它定位成「内部指纹」而非密码学摘要（诚实标注）。节点身份 = (file_id, kind,
  qualified_name)，与 span 无关；未变更文件节点 id 不动，变更文件节点重插获得新 id，
  但所有边/证据同事务重建，外部不暴露 id（查询输出里 id 只在剥掉后比较）。
- **L5 追问：并发场景呢？MCP 长驻服务期间用户在改代码呢？**
  答案要点：写入在单事务内完成 + WAL 快照隔离 → 读者要么见旧图要么见新图，
  没有中间态；MCP 每次工具调用前做 mtime/size 预筛（零哈希），漂移即触发增量重建，
  所以 agent 会话中改文件后查询自动自愈（契约测试里有这条端到端用例）。
  再追「两个进程同时 build」：SQLite 写锁串行化，busy_timeout 排队，正确性无损。
- **通常在第几层答不上**：L3/L4（等价性测试设计与 id 稳定性论证）。要补的知识：
  WAL 与 rollback journal 的隔离差异、为什么单事务里做全部重写反而比部分重写更安全。

### 技术点 3：为什么不用向量检索（差异化论证）

- **L1 追问：现在都是 embedding 检索，你这个的价值是什么？**
  答案要点：代码检索有两种问题：『找语义相关』和『找真有调用关系』。改代码影响评估
  属于后者——embedding 会把「名字相似/注释相似」的函数排前面，但调用关系要么存在
  要么不存在。我给的是确定、可解释、可验证（每条结果有源码证据链）。
- **L2 追问：那语义搜索的场景你怎么办？**
  答案要点：诚实让渡——「这段代码在哪实现某个业务概念」这类模糊查询不是我的目标
  （非目标写在 README）。两者是互补而非竞争：先语义召回候选，再用调用图验证关系，
  是合理的组合架构；我不做前者，所以不用向量库。
- **L3 追问：静态解析的盲区呢？（装饰器路由、DI 容器、monkey patch）**
  答案要点：静态分析有原则性边界。我的策略是「不猜 + 可见」：解析不到的调用点标
  dynamic，在影响面里单独列为间接影响；框架语义（如 Next.js 约定路由）留给语言
  适配器扩展点，但那是插件不是魔法。承认边界比假装全覆盖更可信。
- **L4 追问：JS 没有类型，你的调用图假阳性率多少？**
  答案要点：MVP 里我没有假阳性率数字（诚实说），但结构上控制了来源：歧义不解析、
  遮蔽不解析、内建名单过滤；剩下的假阳性主要来自同名不同类的方法调用（receiver
  类型未知）。改进路径明确：接入 tsc 的类型信息做 receiver 消歧（README 不足节）。
  有个可测的代理指标：dynamic 占比（stats 里有），比例越低说明消歧越干净。
- **L5 追问：如果给你一年时间，你会怎么把两类检索统一？**
  答案要点：图上叠加语义层——节点带 embedding，检索时图约束（调用关系存在性）+
  语义相似度做联合排序；但排序必须可解释（展示「图边证据 + 语义分」两个因子），
  不能退化成黑盒。同时用 tsc 类型表把 dynamic 比例压下来。
  这是方向判断题，答出「统一而不混淆、每个因子可解释」即可。
- **通常在第几层答不上**：L4（敢不敢承认没有假阳性率数字 + 给出代理指标）。
  要补的知识：L4 若追问可以聊 codebase-memory-mcp 等同类项目的做法差异。

## C2 名词党检测（写了名词但可能没真懂的点）

1. **「加权 PageRank」**——如果只能说出「图上跑 PageRank」就是名词党。真懂要能说出：
   边权是什么（调用次数 × 跨文件 1.5 加成）、悬空节点（无出边函数）的质量怎么处理
   （均匀回流到所有节点，否则总质量泄漏、分数不可比）、收敛判据（L1 差 < 1e-6 或 100 轮）、
   为什么不用 in-degree（in-degree 不递归考虑「被重要节点调用」，PageRank 本质是
   不动点迭代）。
2. **「tree-sitter 增量解析」**——注意：我的增量是**文件级**（重解析变更文件），
   不是 tree-sitter 的语法树增量重解析（编辑点 patch）。被问到 must 说清这个区别，
   否则等于没懂自己用了什么。tree-sitter 的 tree.edit + 增量 parse 是行级能力，
   我没有用（文件级 hash 粒度足够 MVP，行级是优化项）。
3. **「WAL 模式」**——真懂要能说出：WAL 下读写不互斥（读快照、写追加），
   我的「单事务全量重写 refs/edges」为什么依赖它（并发 MCP 读 + CLI 写不互踩），
   以及 checkpoint 什么时候发生（自动，DB 体积可控因为每次重写量有限）。
4. **「双向 BFS」**——真懂要能说出为什么双向（出度小入度大不对称，两侧各 d 层
   覆盖 O(b^(d/2)) 对 O(b^d)）、相遇点怎么处理（任一侧扩展的新节点落在对方
   visited 集即相遇，前驱/后继表拼路径）、为什么限深（10 跳外链路对人的决策
   价值趋零且计算爆炸）。
5. **「MCP」**——真懂要能说出传输层是 newline-delimited JSON-RPC 2.0（不是 LSP 的
   Content-Length 帧）、initialize 的版本协商语义、工具错误用 isError 结果而非
   协议错误、stdout 纪律（日志必须 stderr）。这四点任何一个被问倒都算没写过。

| 数字 | 测试集 | 样本量 | 对比基线 | 显著性 | 可信度判定 |

## C5 露馅预测（最可能被问死的问题，直说）

1. **「你的调用图假阳性/假阴性率是多少？」**——没有数字。这不是可以现场编的，
   一编就穿帮（怎么标的 ground truth？）。正确应对：承认没测 + 给出结构性控制
   （歧义/遮蔽/内建三道闸）+ 指出 dynamic 占比这个代理指标 + 说改进路径（标注 200
   个调用点做人工评估，半天工作量，可以现场承诺「下周补上」）。
2. **「tree-sitter 的增量解析你用了吗？」**——高频陷阱题。我没用 tree-level patch，
   是文件级。答不清这个区别 = 没读懂自己依赖的库。背熟 C2-2 的说法。
3. **「为什么不用 libgit2 / git2 crate？」**——考古用了子进程 git blame。
   理由要能说：libgit2 的 blame 对 -C（跨文件移动追踪）支持不全，而 -C 是考古
   可信度的关键；子进程方案代价是环境依赖 git，已做优雅报错。
4. **「10 万行 <X 秒，在生产 monorepo（100 万行 + workspace 协议 + 多 tsconfig）呢？」**
   ——我没测过。正确应对：指出设计上的三个已知放大点（tsconfig extends 只支持
   5 层、workspace 协议未实现、单文件粒度无并行落库）+ 给出量级估算方法而不是硬数字。
5. **「你说增量==全量有 fuzz 证明，fuzz 的变异空间覆盖够吗？」**——5 类变异是
   有限空间；诚实的说法是「覆盖了结构变异的主要类别，但没有做语法级随机生成
   （那是 property-based fuzzing 的下一步）」。

## C6 「不足与重做」标准答案（问倒时用）

- **不足 1：消歧能力受限于无类型信息。** dynamic/ambiguous 引用占比在真实 TS 仓库
  会显著高于有类型的 monorepo。改进：接入 tsc（或用 swc 的类型表）做 receiver 类型
  消歧，把三级解析升级为四级（类型级兜底）。
- **不足 2：证据链是「调用点列表」而不是「程序切片」。** 影响链只给「谁调用谁」，
  不含数据依赖（返回值流向）。严格的影响面应是 SDG（系统依赖图）。改进：在调用边上
  叠加参数/返回值的数据流边（tree-sitter 可抽取赋值关系），优先覆盖 REST handler
  → service → DB 这类高频审计路径。
- **如果重做**：① 起步就把「解析原材料持久化」设计进去（本项目做对了的决策，
  重做保留）；② 语言适配器用独立 crate + trait object 注册，而不是当前的单文件
  模块化——加第二门语言时重构成本更低；③ benchmark 从第一天进 CI，而不是交付前补。
